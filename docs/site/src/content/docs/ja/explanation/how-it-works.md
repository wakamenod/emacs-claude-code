ecc は一本道で、進む向きも一つです。CLI から行が届き、alist になり、モデルを更新
し、モデルが変化を描く側に知らせる。上の層を名前で呼び返すものはどこにもありませ
ん。

```
claude -p --output-format stream-json
        │
        │  1 行 1 JSON オブジェクト、パイプ越しに
        ▼
  ecc-proc        CLI を起動し、stdout を行に割り、JSON を書き返す
        │
        ▼
  ecc-protocol    1 行を入れると alist が出る
        │
        ▼
  ecc-dispatch    type と subtype の表。モデルを更新する
        │
        ▼
  ecc-model       セッション、Turn > Step > Tool の木、待機キュー
        │
        │  フック: ノード追加、ターン終了、リクエスト追加、…
        ▼
  ecc-render      テキストプロパティとオーバーレイで描く
  ecc-chat        メジャーモード、キーマップ、移動
```

## プロセス側

`ecc-proc` がコマンドラインを組み立てて CLI を起動します。変わらない部分はこれ
です。

```
claude -p --input-format stream-json --output-format stream-json \
       --verbose --permission-prompt-tool stdio
```

これに `:connection-type 'pipe` が付きます。stream-json にはこの全部が要ります。
ストリームを full で受け取るための `--verbose` と、権限を求めるツールが、ecc に
は見えないどこかでダイアログを開くのではなく同じチャンネルに返ってくるための
`--permission-prompt-tool stdio` です。コマンドラインの残りはすべて条件付きで、
モデルを与えられたセッションは `--model` を、権限モードを与えられたセッションは
`--permission-mode` を渡す、というふうになっています。

解析済みのメッセージは `ecc-proc-message-function` から出ていきます。そこに自分
を差し込むのが `ecc-dispatch` です。この間接化が層構造の拠って立つ規則です。プロ
セス層は自分の上の層を名前で呼びません。

## JSON はここで止まる

JSON に触ってよいのは `ecc-protocol` と `ecc-proc` だけです（自前のプロセスと話
す `ecc-mcp` と `ecc-inline` は、規則を裏づける例外です）。ほかはすべて Emacs の
データ構造で仕事をします。

そのコードを読むことがあるなら、シリアライズの約束事は知っておく価値があります。
配列はベクタ、`nil` は `{}` に、`null` は `:null`、false は `:false` です。

メッセージの形は実物の CLI から録ったもので、`test/fixtures` に jsonl として置い
てあります。テストスイート全体がその fixture を再生するので、`make test` にネッ
トワークも API キーも `claude` バイナリも要りません。

## 何も捨てない

`ecc-dispatch` は、解析済みメッセージの type と subtype を引く表です。知らない
メッセージも、処理中に発生したエラーも、**トランスクリプトに `unknown` ノードと
して**、そしてセッションのログバッファに残ります。エラーを握り潰すことは決してあ
りません。足元で変わってしまったストリームは、沈黙ではなく画面上の妙なものとして
現れます。

セッションごとにログバッファ `*ecc-log: <名前>*` があり、両方向の生の行がタイム
スタンプ付きで入っています。`<<` が受信、`>>` が送信です。トランスクリプトでの
`L` が開きます。何かおかしいときに最初に見る場所であり、バグ報告に添えるべきもの
です。

## モデルは画面を知らない

`ecc-model` はセッション、Turn > Step > Tool の木、そして回答待ちリクエストのキュー
を持ちます。JSON もプロセスも、それがどう描かれるかも知りません。`ecc-dispatch`
が渡したものを蓄え、変化のすべてをフックで知らせるだけです。
`ecc-node-added-hook`、`ecc-node-updated-hook`、`ecc-turn-started-hook`、
`ecc-turn-finished-hook`、`ecc-request-added-hook`、`ecc-stream-delta-hook` ほか
十数個あります。

このフックが、モデルとパッケージの他の部分との間のインターフェースのすべてです。
レンダラーがそこを聞いていますし、通知も、モードラインも、ダッシュボードも、ファ
イルの同期もそうです。セッションに自分の処理をぶら下げたいときも同じ場所です。
普通のフックで、セッションと変化したものを引数に呼ばれます。

## 描画

`ecc-render` がモデルをバッファに描きます。トランスクリプトとプロンプトが一つの
バッファを共有するので、木はセクションライブラリではなくテキストプロパティとオー
バーレイでできています。

- `ecc-node`（id）、`ecc-depth`、`ecc-heading` が、各テキストが何であるかを示す。
- 畳むのは、本体にかけた `invisible` のオーバーレイ。
- トランスクリプトの一文字キーは `keymap` テキストプロパティから届く。だからメ
  ジャーモードのキーマップはプロンプトでの入力のために空いたままでいられる。

レイアウトは上から、記録をページインするボタン、終わったターン、今のターンを保持
するライブ領域、Files と Tasks のまとめ、状態行、区切り線、そしてプロンプト領域
です。

コストを一定に保っているのは二つの規則です。

- **終わったターンは二度と触らない。** 再描画はライブ領域を消して作り直すので、
  仕事の量は今のターンに比例し、会話の長さには比例しません。
- **どの再描画も `ecc-render--prompt-start` より先を消さない。** 書きかけの下書き
  は、その間にセッションが何をしようと残ります。

ストリーミングされるテキストはそもそも再描画しません。各デルタは、そのノードの末
尾に置いたマーカーの位置に追記され、`ecc-stream-throttle` で間引かれます。

セッションバッファでは font-lock は切ってあります。フェイスは挿入時に付きます。
長いトランスクリプトのスクロールが安いのはそのためです。

## セッションはどこにいるか

問いが二つあるので、ディレクトリも二つです。

**`~/.claude/sessions/<pid>.json`** — 動いている Claude Code は自分について小さな
JSON ファイルをここに書き、止まるときに消します。`ecc-registry` がこのディレクト
リを読みます。Emacs が、自分で始めたのではないセッション――ターミナルの中、別の
Emacs の中、ヘッドレスで動いているもの――を知るのはこの経路です。再開する前に
`ecc-history-resume` がセッションの生存を知るのもここからです。`claude agents
--json` は同じことを報告しますが、5 分の 1 秒かかりポーリングが要るサブプロセス
です。ファイルならただで、しかも情報は多く手に入ります。

**`~/.claude/projects/<cwd>/<session-id>.jsonl`** — 記録です。CLI が書く、1 行
1 JSON オブジェクトのファイル。`ecc-history` はこれを、生きたセッションが使うのと
同じモデルに読み戻します。過去の会話が普通のセッションバッファで開くのはそのため
です。読むのは末尾からで、開くコストは直近の数ターン分、その前は上部のボタンで
ページインします。

記録は**リストではなく木**です。メッセージの編集も、ターンの中断も、二度の再開も、
どれも枝を生やします。`ecc-history-abandoned` が畳むのは現在の線からぶら下がった
枝だけです。`/compact` は新しい根を始めるので、放棄されたものにはなりません。

:::caution[セッションにロックはありません]
同じセッション id を二つのプロセスが再開すると、同じ記録に書き込み、会話は黙って
二本目の枝を生やします。`ecc-tui-open` が二つ目の窓ではなく持ち手の交代である理由
はこれです。ターミナルにセッションを渡す前に、Emacs が動かしているプロセスを中断
して止めます。`ecc-history-resume` がまだ生きているものの再開前に確認するのも、同
じ理由です。
:::

## ソースの並び

読むつもりなら、組み上がっている順序はこうです。

| ファイル | 何であるか |
|---|---|
| `ecc.el` | 入口 -- `ecc-start`、`ecc-resume`、`ecc-kill` |
| `ecc-core.el` | カスタマイズグループ、起動オプション、ログバッファ。他の `ecc-` モジュールに依存しない |
| `ecc-protocol.el`, `ecc-proc.el` | ワイヤ。1 行入れて alist、そして返す JSON |
| `ecc-model.el` | セッション、木、キュー、フック |
| `ecc-render.el`, `ecc-chat.el` | 何が描かれるか、そしてキーマップを持つモード |
| `ecc-perm.el`, `ecc-review.el`, `ecc-plan.el`, `ecc-history.el`, `ecc-mcp.el`, `ecc-tui.el`, … | 1 ファイル 1 機能 |
| `ecc-transient.el` | メニュー |

`test/ecc-<module>-test.el` がモジュールごとに一つあります。新しい振る舞いには自
分のテストが付き、fixture は手書きではなく実物の CLI から録ったものです。
