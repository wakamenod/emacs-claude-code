**Space** とは、タブバーのタブを 1 つ専有する 1 つのプロジェクトのことです。git の worktree はそれ自体が 1 つの Space になり、元のリポジトリの下に表示されます。

これは [`ecc-layout`](/emacs-claude-code/ja/reference/configuration/#ecc-layout) の `spaces` を選んだときの姿です。既定値の `classic` は従来どおりで変わりません。トランスクリプトは main / sub-1 / sub-2 という役割を持つサイドウィンドウに入り、[`ecc-focus-project`](/emacs-claude-code/ja/features/sessions/#focusing-one-project) がその役割を 1 つのプロジェクトに配り直します。

```elisp
(setq ecc-layout 'spaces)
```

## Space で何が変わるか

`classic` では、プロジェクトに絞り込むたびにセッションのウィンドウがゼロから配り直されます。ウィンドウが役割を持っているうちはそれが正しい動きですが、自分で並べ替えたあとでは邪魔になります。

`spaces` ではウィンドウに役割がありません。Space のトランスクリプトは左右に並びます。最初のものはソースの右隣に開き、以降は一番右のものを分割していきます。上下に積まれることはありません。そこから先は普通のウィンドウとして分割・移動・拡大・削除できます。タブとは**ウィンドウ配置そのもの**なので、別の Space に移って戻ってくると、離れたときの配置がそのまま復元されます。

何本並ぶかを決めるのは `ecc-space-session-min-width`（トランスクリプト 1 本が下回ってはいけない桁数）です。もう 1 本分の幅がないときは、狭いウィンドウを作る代わりに、一番長く触っていないセッションがウィンドウを譲ります。譲ったセッションはウィンドウのないまま動き続け、サイドバーと `ecc-toggle` で戻せます。

タブを新しく作る Space は、そこにあるセッションを画面に並べた状態で開きます。最近使った順にソースの右へ、行に次の 1 本分の幅がなくなるまで。入りきらなかったセッションはウィンドウのないまま動き続けます。

**何も動いていない Space に移動すると、そこでセッションが 1 つ起動します。** 常に起動し、設定はありません。ファイルが 1 つ開いているだけで何も話しかけられないタブは壊れて見えますし、Space に移動するのはそこで作業するということだからです。以前の会話の続きから始めたいときは、開いたセッションで `/resume` と打ちます。

`ecc-space-goto` は、録画しか残っていないプロジェクト（以前作業したが、今は何も動いておらずタブもないもの）にも移動できます。これらは意図的にサイドバーには並べず、番号も振りません。番号を振ると `1`-`9` キーの行き先が動いてしまうためです。

```
┌ *ecc-sidebar* ─────┬ タブバー: [ecc] [herdr] [feat-x] ───────────────────┐
│ Spaces             │ ┌ ソース ─────────┬ session-A ────┬ session-B ────┐ │
│ ⚠ [1] ecc        ▾ │ │                 │ (タブライン)  │ (タブライン)  │ │
│    main ↑2 ↓0      │ │                 │               │               │ │
│   └─ ▶ [2] feat-x  │ │                 │               │               │ │
│ · [3] herdr        │ └─────────────────┴───────────────┴───────────────┘ │
│    master          │                                                     │
│                    │   1 つの Space = 1 つのタブ = 1 つのウィンドウ配置  │
│                    │                                                     │
│ Agents             │                                                     │
│ ⚠ ecc   waiting    │                                                     │
│ ▶ ecc-2 running    │                                                     │
│ · herdr    idle    │                                                     │
└────────────────────┴─────────────────────────────────────────────────────┘
```

各セッションウィンドウの中のタブラインは変わりません。そのプロジェクトのセッションを切り替えます。

| キー | コマンド | 動作 |
|---|---|---|
| `C-c c J` | `ecc-space-goto` | Space を名前で選んで移動。録画しか残っていないプロジェクトも選べる |
| `C-c c j` | `ecc-focus-project` | 現在のバッファのプロジェクトに対して同じこと |
| `C-c c z` | `ecc-space-zoom` | このウィンドウでタブを埋める。同じキーで元に戻る |
| `C-c c V` | `ecc-window-focus-source` | この Space のソースをメインウィンドウに出す |
| `C-c c ?` → `X` | `ecc-space-close` | この Space を閉じ、動いているセッションを止める |
| — | `ecc-space-jump` | サイドバーの番号で N 番目の Space に移動 |

タブのウィンドウはあなたのものなので、勝手に組み替えられることはありません。これは裏を返すと、別プロジェクトのファイルを開いた窓はそのまま残り、Space に戻ってきても元には戻らない、ということです。戻す手段が `C-c c V`（`ecc-window-focus-source`）で、この Space のソースをメインウィンドウに出します（`C-u` でバッファを選べます）。例外は、タブにトランスクリプトしか残っていない場合です。これは誰かが並べた配置ではないので、その Space に移動するとコードを読む窓が左側に復活します。

セッションへ移動すると、どのコマンドから移動しても Space ごと切り替わります（`C-c c n`（`ecc-next-attention`）、`C-c c v`、サイドバーの `RET`、ダッシュボードなど）。question や plan は専用のバッファを開きますが、そのバッファは**そのセッションの隣**に出ます ── そのセッションの Space で、transcript を横に置いたまま。使うのは transcript が入っていない窓のうち一番広いもの、つまり Space ではコードを読む窓で、答え終わるとその窓は元のバッファに戻ります。窓が全部 transcript のときだけ、そのうちの一つを分割します。transcript の窓が奪われることはありません。

Space を閉じても worktree のチェックアウトには触れません。タブを手で閉じた場合は何も止まりません。セッションはウィンドウを持たないまま動き続け、`C-c c w`（`ecc-toggle`）かサイドバーから戻せます。

## サイドバー

`C-c c B`（`ecc-sidebar-focus`）でサイドバーを開いてカーソルを移します。同じキーで元のウィンドウに戻ります。`classic` でも使えます。

`classic` でもサイドバーの表示は同じ 2 節で、キーも同じように効きます。違うのは「移動する」の意味です。Space の行で `RET` や `1`–`9` を押すと、従来どおり `ecc-focus-project` がそのプロジェクトに絞り込みます。タブは作られません（数字キーを押したせいで tab-bar が on になるのは、レイアウトを黙って変えてしまうことになるからです）。つまり `classic` のサイドバーは「画面に居座るダッシュボード」で、`spaces` はそれに加えてセッションウィンドウの配置方法そのものが変わります。

サイドバーのウィンドウは `no-other-window` なので、作業中に `C-x o` がそこに落ちることはありません。入口は `C-c c B` です。

```
Spaces
⚠ [1] ecc                 ▾
   main ↑2 ↓0
  └─ ▶ [2] feat-x
· [3] herdr
   master

Agents
⚠ ecc            waiting ×2
▶ ecc-2              running
· herdr                 idle
```

上半分は Space の一覧です。Space が何をしているかを表す印、`1`-`9` キーが取る番号、名前の順に並びます。印は所属セッションのうち最も「うるさい」ものが勝ちます。リポジトリの行の下には git が言うこと ── ブランチと、upstream との差 ── が付きます。worktree は元のリポジトリの下に罫線でぶら下がり、名前はブランチです。1 つのリポジトリの 2 つのチェックアウトを見分けられるのはブランチだからです。

worktree を持つリポジトリの行の右端には `▾` が付き、畳むと `▸` になります。`TAB` か矢印のクリックで切り替わります。畳まれたリポジトリは worktree の分まで答えるので、その中のどれかが答えを待っていれば印がそう言います。

下半分はセッションの一覧で、印・名前・待っているものが並びます。印も色も点滅もタブラインと同じものを使っているので、セッションはどこに描かれても同じことを言います。

| キー | 動作 |
|---|---|
| `RET` | その行の Space またはセッションへ移動 |
| `n`, `p` | 次の行、前の行 |
| `TAB` | リポジトリの worktree を畳む／開く |
| `1`–`9` | その番号の Space へ移動 |
| `c` | この Space でセッションを開始 |
| `W` | この Space の worktree を作ってセッションを開始 |
| `x` | この Space を閉じる |
| `X` | この worktree のチェックアウトを削除 |
| `k` | このセッションを停止 |
| `a`, `d` | このセッションが待っているものを許可／拒否 |
| `g` | git に聞き直して再描画 |
| `q` | サイドバーを隠す |

`ecc-sidebar-width` が幅（既定 28 桁）、`ecc-sidebar-agents-sort` が下半分の並び順です。`spaces`（既定）はセッションを Space ごとにまとめ、`priority` は答えを待っているものを先頭に出します。

## worktree

git の worktree は、1 つのリポジトリの、別のブランチを見ている 2 つ目のチェックアウトです。2 つのセッションが互いの編集を見ずに 1 つのプロジェクトで作業するための仕組みです。

以下のコマンドはどちらのレイアウトでも使えます。

| キー | コマンド | 動作 |
|---|---|---|
| `C-c c C` | `ecc-start-worktree` | リポジトリの隣にブランチをチェックアウトし、そこでセッションを開始 |
| `C-c c ?` → `E` | `ecc-start-in-worktree` | 既にある worktree でセッションを開始 |
| `C-c c ?` → `M` | `ecc-remove-worktree` | そのチェックアウトで動いているセッションを止め、チェックアウトを削除 |

`ecc-start-worktree` はブランチ名を尋ねます。既存のブランチが補完候補として出ますが、既定値は入りません。既存のブランチはそのままチェックアウトされ、無ければ `HEAD` から作られます。

**既にどこかにチェックアウト済みのブランチ**を指定した場合は、拒否せずそのチェックアウトへ移動します。1 つのブランチは同時に 1 つの worktree にしか置けないので、それを指定したということはそのチェックアウトを指しているはずだからです。セッションを開始する前に確認が入ります。チェックアウトのディレクトリ名が ecc の付ける名前と違っていても構いません（Claude Code 自身の worktree は `/` を `+` にしますが、ecc は `-` にします）。探しているのはブランチであってディレクトリ名ではありません。

チェックアウトの置き場所は [`ecc-worktree-directory`](/emacs-claude-code/ja/reference/configuration/#ecc-worktree-directory)（既定 `.claude/worktrees`）です。相対パスはリポジトリからの相対で、`feat/x` の worktree は `<repo>/.claude/worktrees/feat-x` に置かれます。絶対パスは全リポジトリで共有するディレクトリとして扱われ、`<directory>/<repository>/<branch-slug>` に置かれます。

worktree で動いていた**最後の**セッションを止めると、その場でチェックアウトを削除するか聞かれます（`ecc-kill`、ダッシュボードの `k`、サイドバーの `k`、タブの閉じるボタンのいずれから止めた場合も）。同じチェックアウトで 2 本動いていて 1 本だけ止めた場合は聞きません。もう一方から作業ツリーを取り上げる理由がないからです。そのチェックアウトのファイルを開いているバッファは、閉じずに個数だけ確認文に出します。

**ブランチが黙ってチェックアウトと一緒に消えることはありません。** `ecc-remove-worktree` が取り消すのはチェックアウトだけで、作業内容はブランチに残ります。コミットされていない変更があると git は削除を拒否し、強制する前に確認が入ります。

チェックアウトが消えた後で、**ブランチを消すかどうかは別の質問として尋ねられます** ── `ecc-remove-worktree` の後と、worktree の最後のセッションを止めたときのチェックアウト削除の確認の後です。はいと答えると `git branch -d` が走り、どのブランチにも入っていないコミットを持つブランチは `-D` の前にもう一度確認が入ります。detached なチェックアウトにはブランチが無いので尋ねません。別の worktree がまだ持っているブランチも、git が拒否するので尋ねません。

## 作業を worktree のセッションに引き渡す

セッションの中で「worktree を切って X をやって」と頼むと、CLI は放っておけば `git worktree add` を走らせて同じ会話のまま作業を続けます。1 つのセッションが 2 つのチェックアウトを見ている状態です。

[Emacs の MCP サーバー](/emacs-claude-code/ja/start/installation/)を有効にしていると（`ecc-mcp-enabled`）、代わりに `start_worktree_session` というツールがモデルに提示されます。モデルがブランチ名を決めて依頼文を書き、Emacs がチェックアウトを作り、Space として開き、そこでセッションを起動して、その依頼文を送ります。新しいセッションには、どのリポジトリのどのブランチにいるか、どのセッションから渡されたかも伝えられます。元の会話は読めないからです。頼まれた側のセッションは、どこに渡したかを報告し、自分では作業しません。

**新しいセッションに伝わるもの。** 依頼文はモデルが書いた作業の説明ですが、Emacs は同じ会話を見ていた側として事実を足します。触ったファイル（新しいチェックアウトでの名前で）、書いた plan、記録ファイルのパス（依頼文で足りないときだけ読むように、と添えて）、そしてリポジトリ側でコミットされていない変更です。最後のものが効きます ── チェックアウトは `HEAD` から作られるので、未コミットの作業はそこには入りません。先にコミットするか、依頼文にそう書く必要があります。

**残り 2 つの経路は引き戻されます。** モデルが worktree に行く道は他に 2 つあり（CLI 自身の `EnterWorktree` と、Bash の `git worktree add`）、どちらも 1 つの会話が 2 つのチェックアウトを行き来する結果になります。そのセッションがツールを持っているときに限り、Emacs はこれらの許可要求をツール名を挙げた 1 文で拒否し、ユーザーには何も出しません。ツールを持たないセッション（MCP サーバーが無効、あるいは `ecc-mcp-excluded-tools` に入っている）では何も拒否せず、`ExitWorktree` には触れません。`auto` の許可モードでは CLI は Emacs に一切訊きません（`git worktree add` をそのまま実行し、Emacs には要求が届かない。CLI 2.1.272 で実測）。そのため、下書きに *worktree* または *ワークツリー* が含まれていると、ツールを思い出させる 1 行が添えて送られます。このモードでは、その 1 行だけが最後の歯止めです。

他の worktree が既に持っているブランチは、合流せずに拒否されます。1 つのチェックアウトに 2 つのセッションを置くことは引き渡しではないからです。モデルには別の名前を付けるよう伝わります。`M-x` 用のコマンドはなく、Lisp からは `ecc-worktree-delegate` です。

`spaces` では、worktree で開始したセッションはそれ自体の Space を開き、元のリポジトリの下に並びます。
