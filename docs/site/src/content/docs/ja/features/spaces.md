**Space** とは、タブバーに専用のタブを持つプロジェクトのことです。git worktree はそれ自体が 1 つの Space になり、元のリポジトリの下に表示されます。

この動作は [`ecc-use-spaces`](/emacs-claude-code/ja/reference/configuration/#ecc-use-spaces) で有効になり、既定でオンになっています。無効にすると、これ以前の唯一の配置方法に戻ります。トランスクリプトは main / sub-1 / sub-2 という役割を持つサイドウィンドウに入り、[`ecc-focus-project`](/emacs-claude-code/ja/features/sessions/#focusing-one-project) がその役割を 1 つのプロジェクトに割り当て直します。タブもサイドバーも worktree コマンドもありません。

```elisp
(setq ecc-use-spaces nil)
```

## Space で何が変わるか

`classic` では、プロジェクトに絞り込むとセッションウィンドウがゼロから作り直されます。ウィンドウに役割があるなら理にかなっていますが、自分で並べ替えたあとでは都合がよくありません。

`spaces` ではウィンドウに役割がありません。Space のトランスクリプトは横に並びます。最初はソースの右隣に開き、以降は一番右のウィンドウを分割していきます。上下に積まれることはありません。そこから先は普通のウィンドウとして分割・移動・拡大・閉じられます。タブは**ウィンドウ構成そのもの**なので、別の Space に移って戻ってくると、離れたときの配置がそのまま復元されます。

`ecc-space-session-min-width` はトランスクリプトの最小幅（桁数）を設定し、画面に収まる数を決めます。新たにウィンドウを置く空きがない場合、それより狭いウィンドウは作られません。最も長く操作していないセッションがウィンドウを譲り、ウィンドウのないまま実行を続けます。そのセッションはサイドバーまたは `C-c c V` で戻せます。

Space のタブが作成されると、そのセッションが画面に並んだ状態で開きます。最近使った順に、横に次のウィンドウ分の空きがなくなるまでソースの右隣に配置されます。入りきらなかったセッションは、ウィンドウのないまま実行を続けます。

**何も動いていない Space に移動すると、そこでセッションが 1 つ起動します。** ファイルが開いているだけでアクティブなセッションがないタブは壊れて見えますし、Space に移動するのはそこで作業するためです。以前の会話を再開したいときは、開いたセッションで `/resume` と入力します。

これが [`ecc-space-always-session`](/emacs-claude-code/ja/reference/configuration/#ecc-space-always-session) で、既定は on です。Space の振る舞いを決める設定です。on の場合、Space は常にセッションを保持します。開けばセッションが起動し、**最後のセッションを kill すると Space 自体が閉じ**、隣の Space に移動します。プロセスが終了したセッションは消えたわけではありません。`/resume` の復帰先として場所を保持するため、Space が閉じるのは CLI プロセスの終了時ではなく、セッションバッファを kill したときです。off の場合、Space は作業だけでなくコードを読む場所にもなります。開いても何も起動せずソースを表示し、そのプロジェクトの最後のバッファを kill するまで Space は残ります。

**worktree を開くと、その元になったリポジトリも裏で開きます。** worktree をその配下に表示するにはリポジトリが画面上にある必要があるため、元リポジトリも個別の Space として開きます。`ecc-space-always-session` が on ならそこでもセッションが起動します。フォーカスは worktree に残ります。すでに Space を持っているリポジトリはそのままです。

**セッションを kill すると、そのウィンドウも一緒に削除されます。** 以前開いていたバッファ（通常は `*scratch*`）が開いたまま残るのではなく、ウィンドウが削除されて隣の transcript が領域を埋めます。タブの最後のウィンドウは削除できないため、代わりにプロジェクトのソースを表示します。

`ecc-space-goto` は、記録しか残っていないプロジェクト（以前作業したことがあり、現在はプロセスもタブもないもの）にも移動できます。こうしたプロジェクトは意図的にサイドバーには表示せず、番号も振っていません。サイドバーに入れると `1`〜`9` キーに割り当てられた番号がずれてしまうためです。

```
┌ *ecc-sidebar* ─────┬ タブバー: [ecc] [herdr] [feat-x] ───────────────────┐
│ Spaces             │ ┌ ソース ─────────┬ session-A ────┬ session-B ────┐ │
│ ⚠ [1] ecc        ▾ │ │                 │ (タブライン)  │ (タブライン)  │ │
│    main ↑2 ↓0      │ │                 │               │               │ │
│   └─ ▶ [2] feat-x  │ │                 │               │               │ │
│ · [3] herdr        │ └─────────────────┴───────────────┴───────────────┘ │
│    master          │                                                     │
│                    │   1 つの Space = 1 つのタブ = 1 つのウィンドウ配置  │
│                    │                                                     │
│ Sessions           │                                                     │
│ ⚠ ecc   waiting    │                                                     │
│ ▶ ecc-2 running    │                                                     │
│ · herdr    idle    │                                                     │
└────────────────────┴─────────────────────────────────────────────────────┘
```

各セッションウィンドウ内のタブラインは従来どおりで、そのプロジェクトのセッションを切り替えます。

| キー | コマンド | 動作 |
|---|---|---|
| `C-c c j` | `ecc-space-goto` | Space を名前で選んで移動。記録しか残っていないプロジェクトも対象 |
| `C-c c z` | `ecc-space-zoom` | このウィンドウでタブ全体を埋める。同じキーで元の配置に戻る |
| `C-c c V` | `ecc-space-reset-windows` | この Space を新しいタブの初期配置（左にソース、その隣に transcript）に戻す |
| `C-c c ?` → `X` | `ecc-space-close` | この Space を閉じ、内部で実行中のプロセスをすべて停止する（リポジトリなら配下の worktree も含む）。閉じた worktree を削除するか確認する |
| — | `ecc-space-jump` | サイドバーの番号で N 番目の Space に移動 |

セッションに移動すると、どのコマンド（`C-c c n`（`ecc-next-attention`）、`C-c c v`、サイドバーの `RET`、ダッシュボードなど）を使っても、そのセッションの Space に切り替わります。question や plan は、所属するセッションの隣（その Space 内で transcript を横に置いた状態）に専用バッファを開きます。使われるのは transcript の入っていない最も広いウィンドウ（Space ではコードを表示しているウィンドウ）で、質問に答えると元の表示に戻ります。すべてのウィンドウが transcript の場合に限り、その 1 つを分割して開きます。ウィンドウが削除されることはありません。

タブのウィンドウ配置は自動で組み替えられることはありません。そのため、ウィンドウで別プロジェクトのファイルを開いた場合もその表示は維持され、Space に戻っても自動で元に戻ることはありません。レイアウトを復元するには `C-c c V`（`ecc-space-reset-windows`）を使います。新しいタブと同じ規則で並べ直され、左にソース、その隣に直近で使用した順に transcript が並び、横幅が埋まった時点で配置を終了します。サイドバーは現在の位置と幅のまま残り、非表示にしていた場合は再表示されます。唯一の例外は transcript だけが残ったタブです。その Space に移動すると、コード用のウィンドウが自動で再び開きます。

リポジトリの Space を閉じると、その配下に表示されている worktree も一緒に閉じます。これらは画面上で 1 つのグループとして扱われるため、停止する対象をすべて挙げた 1 回の確認を経てまとめて閉じられます。worktree 単体を閉じた場合、リポジトリは開いたまま残ります。一方、worktree を表示するためだけに開かれたリポジトリは、最後の worktree を閉じた時点で一緒に閉じます。

まとまりを閉じると、含まれる worktree の名前を挙げ、**1 つの確認でまとめて削除するか尋ねられます**。Space は閉じられ、中で動いているものもないため、ディレクトリを削除する準備が整っているはずです。「いいえ」と答えると、ディレクトリはそのまま残ります。手動でタブを閉じても何も停止しません。セッションはウィンドウがないまま動き続け、サイドバーや `C-c c V` から元に戻せます。

### タブバーを出すかどうかはあなたが決める

Space はタブであり、タブとはフレーム内の名前付きウィンドウ配置のことです。`tab-bar-mode` はその上に帯を描くだけで、ecc がこのモードを on にすることはありません。`tab-bar-show` が既定の `t` なら `tab-bar-new-tab` が on にし、`nil` に設定されていれば off のままにします。

```elisp
(setq tab-bar-show nil)   ; フレーム上端に帯を出さずに Space を使う
```

タブバーを非表示にしても、Space はまったく同じように動作します。タブの作成・命名・切り替え・クローズはこれまでどおりです。サイドバーには各 Space が一覧表示され、タブバーよりも詳しい情報が確認できます。

## サイドバー

`C-c c b`（`ecc-sidebar-focus`）でサイドバーを開いてカーソルを移します。同じキーを押すと元のウィンドウに戻ります。`classic` でも使えます。

`classic` でもサイドバーには同じ 2 つのリストが表示され、同じキーを受け付けますが、移動の挙動だけが異なります。Space 上で `RET` や `1`–`9` を押すと、タブを作らずに従来の `ecc-focus-project` と同様にそのプロジェクトへフォーカスします。数字キーを押しただけでタブバーが有効になると、レイアウトが予期せず変わってしまうためです。`classic` のサイドバーは画面に常駐するダッシュボードですが、`spaces` はそのダッシュボードに加えてセッションウィンドウの配置方法も変わります。

サイドバーのウィンドウには `no-other-window` が設定されているため、作業中に `C-x o` で切り替わることはありません。切り替えには `C-c c b` を使います。

```
Spaces
⚠ [1] ecc                 ▾
   main ↑2 ↓0
  └─ ▶ [2] feat-x
· [3] herdr
   master

Sessions
⚠ ecc            waiting ×2
▶ ecc-2              running
· herdr                 idle
```

上半分は Space の一覧です。各行には、最も優先度の高いセッションに基づく印、`1`-`9` で使う番号、Space 名が表示されます。各リポジトリの下には git の状態（ブランチと upstream との差）が表示されます。worktree は親リポジトリの下にツリー線で表示され、ブランチ名が付くため、同じリポジトリの worktree を区別できます。

worktree を持つリポジトリの行の右端には `▾` が付き、畳むと `▸` になります。`TAB` か矢印のクリックで切り替わります。畳んだリポジトリにも worktree の状態が反映されるため、いずれかが答えを待っていれば印に表示されます。

下半分はセッションの一覧で、印・名前・待っているものが並びます。印・色・点滅はタブラインと共通のため、セッションはどこに表示されても同じ状態を示します。

| キー | 動作 |
|---|---|
| `RET` | その行の Space またはセッションへ移動 |
| `n`, `p` | 次の行、前の行 |
| `TAB` | リポジトリの worktree を畳む／開く |
| `1`–`9` | その番号の Space へ移動 |
| `c` | この Space でセッションを開始 |
| `W` | この Space の worktree を作ってセッションを開始 |
| `k` | このセッションを停止 |
| `K` | この worktree のディレクトリを削除 |
| `X` | この Space を閉じる |
| `a`, `d` | このセッションが待っているものを許可／拒否 |
| `g` | git の状態を更新して再描画 |
| `q` | サイドバーを隠す |

`ecc-sidebar-width` はサイドバーの幅（既定は 28 桁）を設定します。`ecc-sidebar-sessions-sort` は下半分の並び順を設定し、`spaces`（既定）はセッションを Space ごとにまとめ、`priority` は答えを待っているものを先頭に出します。

## worktree

git の worktree は、独自ブランチを持つリポジトリの 2 つ目の作業ツリーです。2 つのセッションが互いの編集を見ずに同じプロジェクトで作業できます。

以下のコマンドはどちらのレイアウトでも使えます。

| キー | コマンド | 動作 |
|---|---|---|
| `C-c c ?` → `W c` | `ecc-start-worktree` | リポジトリの隣にブランチをチェックアウトし、そこでセッションを開始 |
| `C-c c ?` → `W o` | `ecc-start-in-worktree` | 既存の worktree でセッションを開始 |
| `C-c c ?` → `W k` | `ecc-remove-worktree` | worktree で動いているセッションを停止し、worktree を削除 |

この 3 つのコマンドは専用キーではなく、メニューの `W` の下にまとめられています。worktree 内で作業するためではなく worktree を管理するためのもので、Spaces のキーのように 1 時間に 1 回ではなく、週に 1 回程度しか使わないためです。

`ecc-start-worktree` はブランチの入力を求めます。既存のブランチが補完候補として提示されますが、入力欄は空のままです。既存のブランチはそのままチェックアウトされ、新規ブランチは `HEAD` から作成されます。

**既にどこかにチェックアウト済みのブランチ**を指定した場合は、拒否されるのではなくその worktree に切り替わります。1 つのブランチは同時に 1 つの worktree にしか存在できないため、そのブランチを指定したなら該当する worktree を意図しているはずだからです。その worktree でセッションを開始する前に確認を求められます。worktree の名前が ecc の命名規則通りである必要はありません。ecc が `-` を使う箇所で Claude Code 自身の worktree は `/` を `+` に置換しますが、ecc が検索するのはディレクトリではなくブランチです。

worktree は [`ecc-worktree-directory`](/emacs-claude-code/ja/reference/configuration/#ecc-worktree-directory)（既定値は `.claude/worktrees`）に配置されます。相対パスはリポジトリ基準となり、`feat/x` の worktree は `<repo>/.claude/worktrees/feat-x` に配置されます。絶対パスは全リポジトリで共有され、worktree は `<directory>/<repository>/<branch-slug>` に配置されます。

worktree で動作する**最後の**セッションが終了すると、ecc は即座にその worktree を削除するか確認します。終了方法は問いません（`ecc-kill`、ダッシュボードの `k`、サイドバーの `k`、タブの閉じるボタン、あるいはユーザー操作を伴わない終了のいずれでも同様です）。この確認はセッション終了の少し後に表示されます。セッションが自身のプロセス内部から終了する場合があり、その場では確認を求められないためです。同じ worktree で動いている 2 つのセッションのうち片方を停止しても、もう一方のセッションがまだ使用中であるため削除の確認は表示されません。その worktree 内のファイルを開いているバッファは閉じられず、確認メッセージに件数が表示されます。

**ブランチが削除されることはありません。** `ecc-remove-worktree` が削除するのはディレクトリだけです。作業内容はブランチに残り、ブランチ自体も保持されます。worktree の削除でコミット済みの変更が失われることはないため、確認メッセージが自動で表示されても安全です。ブランチを削除したいときは、いつでも `git branch -d` を実行してください。

**git が clean と見なさない worktree には、もう一度確認が入ります。** コミットされていない変更や未追跡ファイルがあると、git は worktree の削除を拒否します。強制する前に、対象ディレクトリ名を明示した個別の確認が表示されます。

## 作業を worktree のセッションに引き渡す

セッションの中で「worktree を切って X をやって」と頼むと、CLI は単体では `git worktree add` を実行し、同じ会話のまま作業を続けます。その結果、1 つのセッションが 2 つの worktree で作業することになります。

[Emacs の MCP サーバー](/emacs-claude-code/ja/start/installation/)を有効にしていると（`ecc-mcp-enabled`）、代わりに `start_worktree_session` ツールがモデルに提示されます。モデルがブランチ名を指定して依頼文を書くと、Emacs が worktree を作成して Space として開き、そこでセッションを起動して依頼文を送ります。新しいセッションは元の会話を読めないため、どのリポジトリのどのブランチにいるか、どのセッションから送られたかが伝えられます。作業を依頼したセッションは引き渡し先を報告し、自身では作業を行いません。

**新しいセッションに伝わるもの。** 依頼文はモデルによる作業の要約です。ここに Emacs が会話から追跡したコンテキストを追加します。変更したファイル（新しい worktree 内のパス）、作成した plan、記録ファイルのパス（依頼文だけでは不明点がある場合のみ読むよう指定）、そしてリポジトリ内の未コミットの変更です。この最後の点が重要です。worktree は `HEAD` から作成されるため、未コミットの作業は含まれません。先にコミットしておくか、依頼文に明記してください。

**他の 2 つの方法は阻止されます。** モデルが worktree にアクセスする方法は他にも 2 つあります。CLI 独自の `EnterWorktree` と、Bash での `git worktree add` です。どちらの方法も、1 つの会話が 2 つの worktree で作業することになります。セッションがツールを持っている場合、Emacs はツール名を挙げた 1 文でこれらの要求を拒否し、ユーザーに確認を求めることもありません。ツールを持たないセッション（MCP サーバーが無効、または `ecc-mcp-excluded-tools` に `start_worktree_session` が含まれる場合）では、Emacs は何も拒否せず、`ExitWorktree` にも関与しません。`auto` の許可モードでは、CLI は Emacs に一切問い合わせません。`git worktree add` を直接実行するため、Emacs には要求が届きません（CLI 2.1.272 で実測）。そのため、プロンプトの下書きに英語の *worktree* または日本語の *ワークツリー* が含まれている場合、ecc はツールの存在を促す 1 行のリマインダーを添えて送信します。このモードでは、この 1 行が唯一のセーフガードです。この 1 行は送信されますが、ユーザーが書いたものではないため、トランスクリプトのプロンプト部分には配置されません。代わりに、プロンプトの下に折りたたまれた見出し（"1 line Emacs added"）として表示され、通常の見出しと同様に開くことができます。

指定されたブランチをすでに別の worktree が保持している場合、Emacs は合流せずに要求を拒否します。1 つの worktree で 2 つのセッションを動かすことは、作業の引き渡しではないからです。モデルには別のブランチ名を指定するよう伝えられます。専用の `M-x` コマンドはなく、Lisp からは `ecc-worktree-delegate` を使います。

`spaces` では、worktree で開始したセッションは元のリポジトリの下に自身の Space を開きます。
